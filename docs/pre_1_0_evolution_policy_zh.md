# 1.0 前演进政策

> 最后更新：2026-08-15；适用版本：0.6.0-dev

JellyFrame 在 `1.0` 前不承担生产环境向下兼容义务。当前使用者是基于当前源码线
进行开发和评估的用户。架构清晰、唯一权威实现、可测量性能和可维护性优先于保留旧的
预发布行为。

## 原则

- `0.y` 开发线可以有意破坏此前 1.0 前的 API、manifest 字段、package summary、
  diagnostic、工具命令或内部模块边界，只要变更使当前契约更清晰或更安全。
- 不得为了接纳旧 JellyFrame 开发产物而增加 legacy parser、alias、adapter、双代码路径
  或静默 fallback。应移除或明确拒绝过时形式。
- 破坏性变更必须在同一变更中同步更新权威实现、第一方示例、schema、文档和回归测试；
  不维护独立的迁移支持分支。
- 只保留定义当前架构边界的兼容机制：Render Core package 的版本/ABI lock、
  feature-profile 契约，以及明确的 host/port 所有权契约。它们不是 legacy shim。
- 必须保持证据边界。重构不能把设备侧的 `partial` 或 `not-tested` 提升为 `supported`；
  硬件声明仍需要移植侧证据。

## 版本纪律

- `0.y.0` 表示新的活跃 1.0 前契约线，可以包含破坏性变更。
- `0.y.z` 通常是定向修复；但当保留错误或有害的 1.0 前契约会造成重复所有权或长期维护
  成本时，也可以移除它。
- `-dev` 构建是可变开发产物，不是兼容性目标。
- `1.0` 才是支持的公开契约需要兼容性政策，并在必要时提供审慎迁移计划的起点。

当前官方示例和模板的目标为活跃的 `0.6.0` Runtime 与 Render Core line。旧的
`minJellyFrame` 或 `minRenderCore` 值只是历史元数据，不是支持的生产目标。
